What the lecture covers

The first half explains how AI models generate outputs, why plausible answers can still be wrong, and where those errors come from. The second half focuses on how to design more reliable agent workflows using structured tool interfaces, MCP, permissions, and scoped subagents — followed by four hands-on demos.

Central message. Using an agent means asking an AI system to help do the work — "here is my project, please figure out how it works and analyse my data."

Designing an agent means deciding what the AI should and should not have to figure out. Instead of asking it to rediscover everything from source code, we define the workflow explicitly: inputs, allowed parameters, outputs, validation rules, and permissions.

Four demos, one analysis

Every demo runs the same tissue-damage analysis on the same slides with the same trained model. Nothing about the science changes between them. What changes is how much the agent has to infer, and how much it is allowed to do.

Level 1Repository as context
Level 2Explicit MCP interface
Level 3Permission-controlled access
Level 4Scoped subagent delegation

First make the capability explicit, then control who can call it, then narrow what each agent is allowed to do.

1

Original Tissue Analyzer — repository as context

An ordinary research repository. The agent has to work everything out by reading it.

What you will do

  • Run the analysis and the classifier yourself on four synthetic histology cases, then look at the fold-artifact case.
  • Open the same folder in Claude Code and ask it to work out the interface from the repository alone.
  • Probe two wordings: 20x for magnification, and a 50% threshold.
  • Ask it which files it used to decide — repository as context, made visible.

What it teaches

  • An agent can do a great deal with nothing but a well-organised repository.
  • Everything it knows, it inferred from docs, source and config — and a wrong inference looks exactly like a right one.
  • The fold case returns a perfectly ordinary label. Valid output is not the same as trustworthy output.

2

MCP Tissue Analyzer — explicit tool interface

The same workflow, wrapped as MCP tools with a declared schema.

What you will do

  • Run the MCP-adapted tools directly, then register and inspect the server with claude mcp list and claude mcp get.
  • Call analyze_tissue and classify_tissue from inside Claude Code and chain them across all four cases.
  • Send damage_threshold_fraction = 50 and magnification = 25 deliberately, and watch both be refused before anything runs.
  • Then ask in plain English for "20x magnification with a 50% threshold" and see it converted correctly.

What it teaches

  • Claude no longer reconstructs the interface from source; it is handed one.
  • A schema records what a number means — the thing Demo 1 could only put in prose.
  • The MCP lifecycle itself: configure, inspect, remove, restore, connect.

3

MCP + Permissions — restrict the direct paths

The MCP server stays open; direct file and shell access is closed.

What you will do

  • Start from a reasonable-looking policy that denies Read and Edit on data/, and watch it refuse.
  • Then break it yourself — ask for the same file through a shell command, and get it.
  • Patch by naming bad commands, watch that fail too, then close it properly.
  • Practise the four operations: read the rules, add one, remove one, and switch a rule from deny to ask.

What it teaches

  • MCP and permissions are separate layers: MCP defines the capability, permissions decide which direct actions are available.
  • A deny list protects only what you remembered to deny — removing a capability beats blocking its uses.
  • These are guardrails on the agent, not an OS sandbox: the MCP server reads the file Claude cannot open.

4

MCP + Scoped Subagent — delegate with a narrow tool set

A tissue-analyst subagent that holds two tools and nothing else.

What you will do

  • Delegate to a subagent holding only the two MCP tools, then ask the main agent to show you exactly what crossed between them.
  • Prove the two contexts are separate — tell one a fact and ask the other to recall it.
  • Score its answers against the expected values, then probe four edge cases.
  • Find the gap in its rules using the fold-artifact case, and fix the subagent yourself.

What it teaches

  • Two different boundaries: Demo 3 denies a capability you hold; a subagent simply does not hold it.
  • The report is the interface — whatever the subagent saw but did not say is gone.
  • A rule that sounds correct is not the same as one that covers the case you care about.
