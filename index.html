What the lecture covers eight parts

The first half explains how AI models generate outputs and why plausible answers can still be wrong. The second half shows how to build more reliable agent workflows with structured tool interfaces, MCP, permissions, and scoped subagents — ending with four hands-on demos.

PartWhat it covers
Models and scientific workflowsWhat models do, how they differ from algorithms and workflows, and where they appear in research.
How LLMs generateTokens, next-token prediction, context, learned priors, and why plausible output is not always correct.
Attention and TransformersHow attention evolved into self-attention and enabled modern long-context language models.
Why coding agents failContext dilution, competing examples, ambiguous parameters, and silent software errors.
Structured tool interfacesCapability descriptions, schemas, validation, and structured inputs and outputs.
Model Context ProtocolHow MCP exposes selected research capabilities through a common interface.
Permissions and scoped subagentsRestricting direct access, narrowing tool sets, and delegating work to scoped subagents.
Live tissue-analysis demosProgressing from a raw repository to MCP, permissions, and scoped subagent delegation.

Central message. Using an agent means asking an AI system to help do the work — "here is my project, please figure out how it works and analyse my data."

Designing an agent means deciding what the AI should and should not have to figure out. Instead of asking it to rediscover everything from source code, we define the workflow explicitly: inputs, allowed parameters, outputs, validation rules, and permissions.

Advice — how to get the most out of Friday read this

Prepare candidate workflow in mind. The last half hour is the part that outlasts the workshop. Think of a step you already run regularly: the inputs are files, the output is a number, a table or a figure, and you can say what a wrong answer would look like. That last point is the one worth bringing — being able to state the check is what turns a script into a capability worth exposing.

Keep the handout open in a second tab. The vocabulary — model, workflow, tool, schema, permission, scoped subagent — is doing real work in every demo.

Expect not to finish, and do not let that stall you. Every guide on this site is written to be followed alone afterwards. If you fall behind during a block, stop typing and watch; the files are all still there on Saturday.

Pair up if your setup breaks. Two people on one working laptop learn more than one person debugging an install for forty minutes.

The idea to carry forward: the model stays fixed — what changes is the scaffolding around it. Reach decides what an agent can do; memory — files, rules, skills — decides whether it does it the way you need. That distinction is what the Oct 16 session builds on.

Oct 16 · Pattern design intro

Designing an agent for a task you already do. Four patterns to apply to any workflow — who does each step, how much to build, where it runs, and how you would know it went wrong — then a live demo that turns one real task into a skill you can run again.

Design the workflow first. The agent is only one of the boxes. Most steps in a real task belong to you, to a script, or to a check. Friday is about deciding which box is which — and “this does not need an agent” is a perfectly good conclusion.

Bring one small, ordinary task you already do and the five short answers about it: what you do, how you do it now step by step, a sketch of that, what goes in and out of each step — who does it, and whether it belongs in chat, Cowork or Claude Code — and what could go wrong without you noticing. Half an hour is plenty, and a photo of a hand-drawn workflow is a perfect answer.

The study's notes and its data deliberately disagree with each other. Finding the differences is the exercise — and it is a much better first conversation with an agent than asking it to write something from scratch.
