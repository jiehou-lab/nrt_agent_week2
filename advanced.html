Advanced demos

Two more packages, for anyone who wants to go past the four core demos. They are not part of a session — they are worked examples of the two harder shapes a final project can take.

← The four core demos

What these are for

Demos 1–4 turn one analysis package into an agent-ready system. These two take the same package somewhere your own research might need to go: behind a user interface, and onto a queue. Both still run the identical tissue analysis on the identical slides, so anything that changes is the packaging and not the science.

If your project is…Start from
A research workflow exposed as a capabilityDemos 1–4 — define the inputs, ranges, outputs and permissions for one thing you already run.
A workflow plus a user-facing applicationDemo 5 — a form and a text box over the same server, and an explicit answer to which one each control should be.
A workflow on a cluster or a long queueDemo 6 — submit, walk away, come back with a job id. No cluster needed to practise it.

More complicated is not better. A Level 1 project done carefully — clear parameters, real validation, honest reporting of what the tool is unsure about — is worth more than a cluster integration that nobody can reproduce. Pick the shape that matches the work you actually do.

The two packages

5

Streamlit research app — the same analysis, two routes

A web front end over the Demo 2 MCP server, built to make one distinction visible.

What you will do

  • Run the analysis from a form — no language model anywhere in the round trip.
  • Widen the slider past the legal range and watch the server refuse what the form allowed.
  • Ask for the same thing in English and watch Claude Code convert 20x and 45% into valid arguments.
  • Delete one line from settings.json and see the request quietly do less than you asked.

What it teaches

  • A button means you decided at design time; a text box means the model decides at run time.
  • Validation belongs where the work happens, not in the widget.
  • In -p mode nothing can answer a permission prompt, so an unapproved tool is simply skipped — silently.

6

Scheduled batch agent — a job that outlives the conversation

Four tools, no shell: submit, check status, collect results. The work happens somewhere nobody is waiting.

What you will do

  • Submit eight slides and get an id back in under a second — before anything has been analyzed.
  • Ask an unrelated question while it runs, then /exit, start a fresh session, and collect the job by id.
  • Read the report, then count what its summary did not mention.
  • Fix the fifteen-line function that decided what the reader is told.

What it teaches

  • An agent that waits is an agent that dies with a closed laptop; state belongs outside the conversation.
  • A job id is a handle a human can carry between sessions; a context window is not.
  • Demo 4's missing warning, at batch scale — three of eight slides flagged, none of them in the summary.
  • Denying Bash stops being a teaching exercise once a real queue is on the other side.

ZIP · Python 3, standard library only. Runs on a laptop; one variable switches it to Slurm.

A caution about the cluster path

Demo 6's local simulator is exercised and works. Its Slurm backend is written but has not been run on a cluster by the course staff — partitions, modules, filesystem layout and accounting policy differ at every site. Read scheduler/backend.py and slurm/job_template.sbatch before you use them, and test with one slide before you submit eight hundred.

The pattern is the lesson. Slurm is an implementation detail, and so is whatever replaces it.
